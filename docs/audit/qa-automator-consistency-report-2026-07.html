Saneamiento ejecutado — 2026-07-17

Los 22 hallazgos están resueltos en la rama fix/saneamiento-auditoria-2026-07 (6 commits, uno por fase: F1 críticos → F2 verdad documental → F3 contratos/EOL → F4 pulido → F5 regeneración). Decisiones aplicadas: MCP portable con node + node_modules/playwright/cli.js (verificado, sin shim cmd/npx); referencias a SPEC/METODOLOGIA eliminadas de los prompts distribuidos; .gitattributes con LF; pre-flight con warning en navegación sin URL (fail-closed descartado: rompería las tools sin URL legítimas); compliance-verdict.json documentado en ruta plana.

Pendiente manual (no verificable desde esta máquina): confirmar en un tester con SOLO el plugin instalado que Task(subagent_type: 'ia4d-reviewer') resuelve sin prefijo. Nada se ha pusheado — la rama es local.

Resumen ejecutivo

La sincronización de contenido entre las tres copias (repo → plugin → template/payload) está bien: los 12 agentes y los commands son byte-idénticos salvo line-endings, la versión 0.3.2 es consistente en package.json, plugin.json y el payload, y todos los scripts, exports y ficheros de config que los prompts citan existen. El problema no es el motor: es la documentación que acompaña al workspace desplegado, que quedó anclada a la distribución anterior (pre-plugin, v0.3.1) y a estados de versiones anteriores (v0.1/v0.2).

Tres hallazgos bloquean directamente la misión de "pasarle el agente a otras personas": (C1) toda la guía del workspace enseña commands /qa-automator:* que ya no existen — el plugin los publica como /ia4d-qa-automator:*; (C2) el command healthcheck describe el mundo v0.1 (13 subagents en .claude/agents/, versión v0.1.0) y en un workspace desplegado reportará fallos falsos; (C3) el .mcp.json distribuido usa cmd /c — solo arranca en Windows.

C1 Toda la documentación del workspace desplegado enseña commands que no existen Críticonamespace

Desde v0.3.1 (distribución híbrida) los commands los publica el plugin con namespace /ia4d-qa-automator:*, y el workspace desplegado ya no lleva .claude/commands/. Pero la guía que el tester lee — CLAUDE.md, README.md y los README de los 5 labs — usa el namespace viejo /qa-automator:* en todas sus ~25 menciones. En el template hay cero ocurrencias del namespace correcto. Un tester que siga el quickstart tecleará un comando que no existe en su primer contacto con el producto. Los commands del plugin (init, help) sí usan el namespace bueno, lo que agrava la confusión: el punto de entrada dice una cosa y la guía interna otra.

Evidencia
  • template/CLAUDE.md:66-84, 99, 111, 132 — tabla de modos + bloque de comandos + 3 menciones sueltas
  • template/README.md:26, 44 — quickstart paso 4 y cierre de labs
  • template/examples/01-saucedemo/README.md:92, 109, 123
  • template/examples/02-parabank/README.md:20, 45, 55, 68
  • template/examples/03-orangehrm/README.md:20, 43
  • template/docs/references/composition-rules.md:5 · audit-log-schema.md:39 · style-contract-schema.md:121
  • plugin/.../scaffold/payload/** — mismas copias (payload = template)
Cómo repararlo

Sustitución global /qa-automator: → /ia4d-qa-automator: en las fuentes del template (recuerda la regla: se edita en el repo y se propaga con npm run build:plugin, que ya corre build:template). Ojo: build-template.mjs preserva CLAUDE.md, README y examples del template — esos hay que editarlos directamente en template/ y regenerar solo el plugin. Añadir un check al healthcheck o al build que grepée el namespace viejo evitaría la regresión.

C2 healthcheck.md describe el mundo v0.1 y contradice al script real Críticodesactualizado

El command instruye listar los 15 subagents bajo .claude/agents/ — pero en un workspace desplegado solo viven los 3 nativos de Playwright (los 12 ia4d vienen del plugin). Espera versión v0.1.0 (vamos por 0.3.2), dice "13 subagents" cuando su propio desglose suma 15 (3+4+3+2+3), clasifica spec-parser y spec-refiner como stubs (funcionales desde v0.2), y verifica hooks/hooks.json cuando el wiring real es .claude/settings.json — exactamente lo que el script src/scripts/healthcheck.ts:104 ya chequea bien. No menciona npm run qa:healthcheck, que es el healthcheck real (21 checks, incluido el arranque del MCP). Resultado con testers: el command reporta "faltan 12 subagents" en un workspace perfectamente sano.

Evidencia
  • .claude/commands/qa-automator/healthcheck.md:12-17 — listado bajo .claude/agents/
  • healthcheck.md:33 — "ia4d-qa-automator v0.1.0"
  • healthcheck.md:34 — "13" vs desglose que suma 15; spec-parser/refiner como "stubs"
  • healthcheck.md:20 — verifica hooks/hooks.json (no cargado por Claude Code)
  • src/scripts/healthcheck.ts:97-104 — el script ya asume el modelo híbrido (3 nativos + settings.json)
Cómo repararlo

Reescribir el command para delegar: "ejecuta npm run qa:healthcheck y presenta su salida verbatim" (mismo patrón que ya usa config.md con el contract-validator — hard rule #5). Eliminar la lista manual, la versión y el conteo hardcodeados. Un solo lugar con la verdad: el script.

C3 .mcp.json distribuido usa cmd /c — el MCP solo arranca en Windows Críticoportabilidad

Las tres copias del .mcp.json (repo, template, payload) declaran el server como "command": "cmd", "args": ["/c", "npx", ...]. En macOS/Linux cmd no existe: el MCP playwright-test no arranca, el planner queda sin tools de navegador y la guarda anti-fabricación aborta el run. Todo el motor S2/S3/S4 muere en el primer paso para cualquier tester fuera de Windows, y el mensaje de error no apunta a la causa. Si el piloto es 100% Windows es tolerable, pero hay que decidirlo, no heredarlo.

Evidencia
  • .mcp.json:3-11 — "command": "cmd" (repo)
  • template/.mcp.json · plugin/.../payload/.mcp.json — idénticos
  • template/README.md:14 — requisitos no mencionan "solo Windows"
Cómo repararlo

Opción a: "command": "npx" directo (verificar en Windows — el wrapper cmd /c suele ponerse porque npx es un .cmd en win32; probar antes de cambiar). Opción b: mantener cmd /c y declarar "Windows-only por ahora" en los requisitos del README + un check de plataforma en el healthcheck. Lo inaceptable es la situación actual: falla silenciosa y sin documentar.

Los prompts distribuidos con el plugin instruyen leer SPEC.md ("§4 Code style", "§6 Boundaries", "§7 Roadmap"...) y METODOLOGIA AISD.md, pero ninguno de los dos viaja en el payload ni en el plugin. A5 Fichero fantasma con ruta Windows literal en el root + basura trackeada en git Altohigiene-repo

En el root vive un fichero llamado literalmente c:Workspaceinetum-qa-agents-worspace-dev.workcompliance-verdict.json: una ruta absoluta de otro clon (c:\Workspace\inetum-qa-agents-worspace-dev\.work\compliance-verdict.json — el remote con el typo "worspace") a la que Bash le comió los backslashes y la creó como nombre de archivo. Contiene un veredicto de compliance de una URL de producción de Mapfre. Es el failure-mode predecible de los agentes sin tool Write que escriben JSON "a mano vía Bash" (compliance-checker, reviewer, pii-scanner) recibiendo rutas Windows. Además: log.log (transcripción de sesión) está commiteado, y flujo-qa-automator.pptx vive en el root en vez de docs/.

Evidencia
  • c:Workspaceinetum-qa-agents-worspace-dev.workcompliance-verdict.json — root; verdict W1 sobre mapfre.es/ahorro-inversion
  • .git/sourcetreeconfig.json:28 — remote "inetum-qa-agents-worspace-dev" (origen del typo)
  • ia4d-compliance-checker.md:27 — "write to .work/compliance-verdict.json via Bash — this agent has no Write tool"
  • git ls-files — log.log y flujo-qa-automator.pptx TRACKED; tmp/ y log_ejecucion.log ya ignorados
Cómo repararlo

Borrar el fichero fantasma; git rm --cached log.log + añadir /log.log al .gitignore; mover el .pptx a docs/ o ignorarlo. Root cause: en los agentes que escriben por Bash, exigir rutas con forward-slashes ("usa siempre /, nunca \") o darles tool Write — el reviewer ya sufrió el problema equivalente con el escapado de JSON (fix v0.3.2), este es el mismo patrón de fragilidad.
